# Spike: sandbox-runtime under bubblewrap inside a k3s pod

Date: 2026-10-26
Node: `homelab` (192.168.5.2), Ubuntu 22.04.5, kernel 6.8.0-138-generic, k3s v1.36.4+k3s1,
containerd v2.3.4-k3s1.36, Cilium 1.20.1, AppArmor enabled (64 profiles),
`kernel.unprivileged_userns_clone=1`, `kernel.apparmor_restrict_unprivileged_userns=0`.

Manifest: [`spike.yaml`](spike.yaml). Two pods in the existing `testing` namespace ran the same
script (`node:22-bookworm`, apt `bubblewrap socat ripgrep`, `npm i -g @anthropic-ai/sandbox-runtime@0.0.81`),
then were deleted.

| Pod | `hostUsers` | `procMount` | AppArmor / seccomp on container |
|---|---|---|---|
| `srt-spike-userns` | `false` (pod user namespace) | `Unmasked` | both `Unconfined` |
| `srt-spike-plain` | default (host uids) | default (masked) | both `Unconfined` |

## Conclusions

1. **Full-strength srt works in an unprivileged pod** on this cluster when the pod runs in a user
   namespace (`hostUsers: false`) with `procMount: Unmasked` and the sandbox container's AppArmor
   and seccomp profiles set to `Unconfined`. No node changes were needed: kernel 6.8, containerd 2.3
   and k8s 1.36 already satisfy the user-namespace and `ProcMountType` GA requirements.
2. Root inside the pod is host uid 2889613312, so even the pod's "root" is unprivileged on the node.
   The sandboxed command itself runs as a non-root uid with every capability dropped.
3. Without the user namespace the runtime's masked `/proc` blocks bubblewrap's fresh procfs mount,
   exactly as upstream documents; only `enableWeakerNestedSandbox` works there, and it leaks the
   container's process table into the sandbox (18 pids visible instead of 4).
4. `enableWeakerNestedSandbox` is therefore kept only as a values.yaml fallback for clusters that
   lack user-namespace support, not as the default.
5. Run the wrapped process as a non-root user (uid 1000). The uid 0 variant works but trips over
   ordinary DAC on files it does not own once capabilities are dropped, and upstream recommends a
   non-root caller.
