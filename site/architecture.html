Architecture

How the sandbox keeps Claude contained

We stacked three boundaries around every agent: a powerless container, a locked room inside it, and a network fence around both. Pick a scenario below and step through it to see which layer makes the call at each point.

In plain terms

Most of the time the layers just get out of the way: Claude runs a command, reaches a site it's allowed to reach, and gets its answer. The third scenario is the interesting one. It shows a piece of hostile code trying five different ways to get out, and which layer stops each attempt.

Outgoing traffic

One list of allowed sites, checked twice

The allowed-sites list lives in one place in each sandbox's settings, and we render it into two different checks. If one of them is ever misconfigured, the other still holds.

Options we turned down

Three shortcuts that look simpler and aren't

Give the pod full privileges

The sandbox would work, but if anything escaped it would be root on the server. The private user list gets us the same result with nothing to lose.

Two sandboxes, one inside the other

Claude Code has its own sandbox for shell commands. Running it inside ours means relaxing a rule that would weaken the outer walls. One strong layer around everything beats two that undercut each other.

A firewall script inside the pod

That needs network-admin permission inside the very container we're trying to lock down. A cluster policy outside the pod needs no permission and can't be edited from inside.
