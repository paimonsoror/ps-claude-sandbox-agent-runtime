Overview · homelab build, October 2026

A safe place for Claude to do real work.

We wanted our Claude agents to run commands, edit code and install packages on our own hardware, without handing them the keys to the whole network. So we built a sandbox in our homelab Kubernetes cluster. Claude can work freely inside it, reach only the websites we allow, and can't touch anything else on the network.

In plain terms

Think of it as a locked workshop for a contractor. Inside, they have every tool they need and a workbench they can make a mess on. They can phone a short list of suppliers we picked. They have no key to the rest of the house, and even if they climbed out the window they would land in a fenced yard. That is the whole design: a workbench, a supplier list, and a fence.

Why we needed it

An agent that can run commands needs somewhere safe to run them

A laptop is the wrong place

Claude Code can sandbox its own shell commands on a laptop, but the laptop has to stay open, and some of Claude's helpers run outside that sandbox. We wanted a machine that is nobody's daily computer and stays on.

A plain container isn't enough

Kubernetes runs programs in containers, but by default "root" inside a container is root on the server. We needed the sandbox to be powerless on the server even if something inside goes wrong.

The network is the real risk

Anything an agent can read, it could send somewhere. So the most important rule is where it is allowed to connect. We enforce that list in two separate places.

We wanted to prove it, not claim it

We measured the build against published security guidance from OWASP, NIST, Anthropic and others, and we list the gaps openly on the Controls page.

What we built

Two kinds of sandbox from one recipe

Workspace

Claude Code, living in our cluster

A copy of Claude Code runs inside the sandbox around the clock. You open it from the Claude app on your phone or from claude.ai/code in a browser, and every session gets its own clean copy of the project to work in. Nothing on our network has to accept incoming connections: the sandbox calls out to Anthropic, and Anthropic relays your messages.

Agent worker

A place for Anthropic's hosted agents to work

Claude Managed Agents are agents Anthropic runs for you. Normally their tools run in Anthropic's cloud. With this worker, their tool calls (running a command, writing a file) happen inside our sandbox instead, so the work and the files stay on our hardware.

How it holds

Three layers, each one assuming the last might fail

Layer 1

A powerless container

Each sandbox runs in a Kubernetes pod that has its own private user list. "Root" inside it is a nobody on the real server. The program also runs as a regular user, with every special permission removed and the system files read-only.

Details →
Layer 2

A locked room inside it

Anthropic's sandbox-runtime wraps Claude in a second boundary. It can only write to its own work folders, it can't see other programs, and it has no network card at all. Every connection has to go through a gatekeeper that checks the allowed-sites list.

Details →
Layer 3

A fence around the pod

The cluster's network policy repeats the same allowed-sites list at the network level, and blocks everything else, including the rest of our home network and the other apps in the cluster. Nothing can connect in.

Key terms

The words you'll see on these pages

Sandbox
A walled-off space where a program can run without being able to affect anything outside it.
sandbox-runtime (srt)
Anthropic's open-source tool that puts a program in a sandbox. Claude Code uses it on laptops; we use it on our server.
bubblewrap
The Linux tool srt uses to build the locked room: its own view of files, its own process list, no network.
Kubernetes, pod
Kubernetes runs programs across servers. A pod is one running unit, usually one container.
User namespace
A Linux feature that gives a pod its own private list of users, so its "root" is powerless on the real server.
Allowlist, egress
Egress is outgoing network traffic. The allowlist is the short list of websites a sandbox may reach. Everything else is refused.
Network policy (Cilium)
Firewall rules the cluster enforces around each pod. Cilium is the networking layer our cluster uses.
GitOps, ArgoCD
We describe the cluster in a Git repository, and ArgoCD makes the cluster match it. To change something, we change a file.
Helm chart
A reusable package of Kubernetes settings. Ours turns a five-line sandbox description into everything the sandbox needs.
Remote Control
A Claude Code feature that lets you drive a Claude Code session on another machine from your phone or browser.
Claude Managed Agents
Agents that Anthropic hosts and runs. A "self-hosted environment" lets their tools run on your machines instead.
ADR
Architecture Decision Record: a short note that says what we decided, why, and what we turned down.
