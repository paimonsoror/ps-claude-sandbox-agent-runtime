Controls

How our build stacks up against published security guidance

Security groups and vendors have published a lot of advice on how to run AI agents safely. We collected about sixty concrete controls from OWASP, NIST, Anthropic, the Cloud Security Alliance, Kubernetes, MITRE and several commercial sandbox providers, and checked our build against each one. The full list, with sources, is docs/controls-matrix.md.

In plain terms

Each control gets one of three marks. Met means we do it and can show it. Partial means we do most of it and say what is missing. Gap means we don't do it yet. We are in good shape on the things that matter most for a homelab: what Claude can write, where it can connect, and what it can see. The gaps are things a company would need before rolling this out widely, and we list exactly what would close each one.

We score well where the sandbox runtime and Kubernetes do the heavy lifting: files, network access, no cluster credentials, no root. The gaps sit in three places that matter to a company and that a homelab can live with for now.

The three gaps

What a company would need to add first

kernel

A separate kernel for each sandbox

All our sandboxes share the server's operating system kernel. A bug in the kernel could, in theory, let one escape. The guidance from OWASP, Kubernetes and the commercial sandbox providers is to give each sandbox its own small virtual machine.

What it takes: servers that support virtualisation, and one setting in our chart (runtimeClassName) to run each sandbox in gVisor or a microVM. That also brings us up to Kubernetes' strictest pod security level.

credentials

Keep passwords and keys out of the sandbox

Today Claude can read its own login file and the GitHub token it uses, because it needs them. Anthropic's own cloud sessions, Docker and Daytona do better: the real key is added on the way out, so the sandbox never sees it.

What it takes: turning on sandbox-runtime's credential masking (which needs it to inspect encrypted traffic), short-lived GitHub tokens per session, and Anthropic's workload identity sign-in instead of a stored login.

audit

Tamper-proof, central records

OWASP and MITRE both ask for a record of every action an agent takes, kept where it can't be altered. Today our logs go to Loki and Claude's session history stays on the sandbox's disk.

What it takes: sending Claude Code's telemetry to our collector, recording every refusal as a structured event, and storing it all somewhere that can't be edited, with a retention policy.
