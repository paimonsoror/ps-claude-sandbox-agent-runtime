Fleet management

Who runs the dashboard when there are hundreds of sandboxes?

Two sandboxes are easy to keep an eye on. A company with hundreds needs to see them all, scale them up and down, and spot the broken ones. We looked into how Anthropic expects that to work, and whether the Claude Console is meant to be that control panel.

The short answer

Anthropic runs the brain: the model, the agent's reasoning, the queue of work and the session history. You run the hands: the machines and sandboxes where commands actually execute. The Claude Console shows you the brain side very well. It doesn't show or manage the hands. There is no Anthropic dashboard that lists our sandbox pods, tells us which one is unhealthy, or scales them. That part is expected to come from your own tooling, which for us is Kubernetes, ArgoCD and Grafana.

Agent workers

For Managed Agents, the Console is the brain's dashboard

What you get

In the Claude Console

  • Environments: create a self-hosted environment, generate and revoke its key. Keys can only be made here.
  • Sessions: every session with its status, agent, tokens, cost, a timeline and a full transcript of every tool call.
  • Workspaces: separate spend limits, rate limits and keys per team, up to 100. Anthropic suggests one workspace and environment per trust boundary.
  • Webhooks: get notified when a session starts, goes idle or ends.
  • Tracing: send OpenTelemetry traces of agent turns to your own collector.
What you don't get

No view of the workers

  • No list of workers, no per-worker health, no "this one stopped".
  • Queue numbers come from an API call, not a page: how many tasks are waiting, how many were claimed, and a count of workers that checked in during the last 30 seconds.
  • No autoscaler. Anthropic's guidance is to watch the queue numbers and scale your own workers.
  • No metrics endpoint on the worker. You get structured logs and, from the SDK workers, traces.
Claude Code workspaces

For Claude Code, there are two products, and we used the lighter one

What we built on

Remote Control

Run claude remote-control anywhere and drive it from your phone. That's what our workspace pod does. For admins, claude.ai has an on/off switch for Remote Control and a "trusted devices" option. It does not have a list of the machines running it, and Claude Code's own telemetry doesn't name the machine unless you tag it yourself.

Great for one person or a small team. Not built for fleet management.

Built for fleets

Self-hosted environments

A separate Claude Code feature, in public beta for Team and Enterprise plans. You run runners on your own infrastructure. People start sessions from claude.ai/code and pick your environment, and the sessions run on your runners. Admins get a status page (Healthy or No runners), an Activity tab with each runner and any failed sessions, and a Retry button.

Each runner exposes Prometheus metrics, Anthropic ships an example Kubernetes Deployment and an autoscaling orchestrator, and the docs tell you to feed its pending-sessions metric into Kubernetes autoscaling (HPA or KEDA).

What this means for us. If we take this design into an enterprise, the Claude Code workspace kind should move from Remote Control in a pod to self-hosted environment runners in our sandbox pods. Our sandbox, network fence and GitOps delivery stay the same. What we gain is Anthropic's admin view, runner metrics and autoscaling hooks. We recorded this as ADR-0017.

What we'd build

A fleet view, made from tools we already run

Everything a fleet dashboard needs already exists in our cluster, or comes from the steps above. This is the plan we wrote down, in the order we'd do it.

One Grafana dashboard for every sandbox

Pod status per sandbox from Kubernetes, sync health per sandbox from ArgoCD (each sandbox is already its own ArgoCD app), refused connections from the network fence, and sandbox-runtime's refusals from the logs.

plan 4
Queue numbers for the agent workers

A small exporter that reads waiting tasks and live worker counts for each environment and hands them to Prometheus. It needs an Anthropic API key, so it runs outside the sandbox namespace with a key scoped to one Console workspace.

plan 4
Scale workers on those numbers

With one sandbox per session (plan phase 6), KEDA can add worker pods when tasks are waiting and remove them when the queue is empty.

plan 6
Move workspaces to self-hosted environment runners

On a Team or Enterprise plan: the same sandbox, running Anthropic's runner instead of Remote Control, which adds the admin Activity view and runner metrics.
