Where our principal engineer wants this to go, and how far we are

"We basically are asking for an on-premise version of Google's control plane around substrate. But with Lambda microVM with OpenShell as a backend provider."a principal engineer, 2026-10-26

Our principal engineer summed up the target in one sentence. It packs a lot of industry shorthand into a few words. This page unpacks each term, shows what we built next to it, and explains every difference.

In plain terms

Today we hand-build each sandbox from a recipe and it runs until we remove it. The target adds a manager that creates a fresh sandbox for every task, keeps some warm and ready, and cleans them up afterwards, and it lets that manager put each sandbox in a choice of containers, including a tiny virtual machine of its own. What we built is the bottom layer of that picture, and it carries over. Tap any underlined term in the quote for its definition.

The sentence, assembled

A manager on top, a choice of walls underneath, our sandbox at the bottom

Read the sentence as two halves. The control plane is the manager: it creates a sandbox when work arrives, keeps spares warm, routes each session to its sandbox and cleans up afterwards. The substrate is what each sandbox is built from, and the sentence names two options: a microVM, which gives each sandbox its own tiny virtual machine and kernel, and OpenShell, which polices what the agent inside may do. They solve different problems and can be combined. Nobody sells all of this as one product you can run on your own hardware today.

North star: a lifecycle API on top, swappable isolation underneath, the same image at the bottom.

How we get there

Four steps, each one useful on its own

Keep today's chart for our workspaces

They are long-lived developer machines; a lifecycle API adds nothing for them.

now
Control plane first: per-session Managed Agents sandboxes

Install kubernetes-sigs/agent-sandbox; replace the always-on worker with a poller that creates one SandboxClaim per work item from a SandboxTemplate built from this image; evaluate the warm pool. The on-premises half of the sentence with the substrate we already have.

Gate: a controller install; its own ADR and app-of-apps entry.

plan 6
Substrate second: a microVM RuntimeClass

When a KVM-capable node exists, add Kata or a libkrun-backed runtime to the template and run srt in weak mode inside it. This also closes the PSS restricted gap.

Gate: hardware with KVM.

later
Policy layer evaluation: OpenShell vs srt

Compare on the controls rows it would change: credential brokering, per-binary L7 egress, policy prover. Switch only if it wins there and Anthropic lists it as a provider; otherwise pursue srt's own credential masking and TLS termination.

Gate: an OpenShell release on Anthropic's provider list.

later

The one-line answer for our principal engineer. Same substrate shape (hardened image plus a policy document, deny-all egress, no credentials in git), the control plane and the kernel boundary still to come, each blocked by one concrete thing: a controller install, and a node with KVM.
