Decisions

Seventeen decisions, and why we made each one

Every significant choice we made is written down as an Architecture Decision Record (ADR): what we decided, why, what it costs, and the options we turned down. Each card below gives the plain-language version. Open it for the technical detail. The full records live in docs/adr/ in the repository.

Why we write these down

Security rules get loosened when nobody remembers why they exist. Writing the reason next to the rule means the next person, or the next Claude agent, can see what a change would undo. We never edit an accepted decision. If we change our mind, we write a new one that replaces it.

0001
We write down every decision

One short file per decision, never edited after it's accepted.

Accepted
Details

Why

This will be run for years by one person and extended by agents who weren't there. The reason behind a security boundary is the first thing to be forgotten.

Turned down

A single design document edited over time (loses the history); commit messages only (hard to find).
0002
It runs on our existing homelab cluster

The server already had everything the sandbox needs, so we didn't install anything on it.

Accepted
Details

What we found

Ubuntu 22.04 with kernel 6.8, k3s 1.36.4, containerd 2.3.4, Cilium 1.20.1, ArgoCD 2.14.9. Kernel 6.8 and Kubernetes 1.36 already support pod user namespaces.

Turned down

The TrueNAS lab VM with KIND: easier to throw away, but not where our GitOps runs.

The cost

One server means every sandbox shares one kernel. Our layers make up for that; a separate kernel per sandbox is a future step.

Note

The repository-layout half of this decision was replaced by 0014.
0003
Each pod gets its own private user list

That makes "root" inside the sandbox a powerless user on the server, and it lets the sandbox run at full strength.

Accepted
Details

The problem

bubblewrap needs to set up its own view of running processes. A normal Kubernetes pod hides parts of that view, so bubblewrap fails, and the only workaround upstream offers is a weaker mode.

What we did

hostUsers: false (a pod user namespace, GA in Kubernetes 1.36) plus procMount: Unmasked, which Kubernetes only allows when the pod has its own user list. Also: run as user 1000, drop every capability, read-only root file system, AppArmor and seccomp left to the sandbox runtime.

Evidence

We tested both shapes on the real server. Full strength passed every check; a normal pod only worked in the weaker mode, and then the sandbox could see every process in the container.

The cost

Kubernetes' strictest pod security level doesn't allow these settings. The private user list is what makes it safe anyway.

Turned down

A privileged pod (an escape would be root on the server); the weaker mode as the default.
0004
One recipe, two kinds of sandbox

A workspace for Claude Code, and a worker for Anthropic's hosted agents.

Accepted
Details

Why

Our main use is Claude Code itself. The worker lets Managed Agents sessions run their tools on our hardware. Both use the same container, the same walls and the same network rules.

Later

A gateway so a laptop's Claude Code can run commands in the homelab, and a kind for our own Agent SDK apps.
0005
One strong wall around everything, not two weaker ones

The sandbox wraps all of Claude Code, including its plugins and helpers. Claude Code's own command sandbox is switched off inside it.

Accepted
Details

Why

Claude Code's built-in sandbox only covers shell commands; its MCP servers and hooks would run outside. Anthropic's docs suggest wrapping the whole process instead. Running Claude Code's sandbox inside ours would mean allowing nested sandboxes, and upstream warns that weakens the outer one.

The cost

Claude doesn't see "this was blocked" notes inline; the sandbox's own log records them instead.

Turned down

Claude Code's sandbox only; both layers stacked.
0006
One list of allowed sites, enforced in two places

The sandbox's gatekeeper and the cluster's network fence both use the same list, so one mistake can't open the door.

Accepted
Details

Why

The gatekeeper only governs what runs inside the locked room. Anything else in the pod would otherwise see the whole network, including our home network and every app in the cluster.

How

sandbox-runtime's allowlist with strictAllowlist, plus a CiliumNetworkPolicy allowing DNS and HTTPS to the same names. Private address ranges are refused even for allowed names. Nothing can connect in.

What it can't do

Neither check opens encrypted traffic, so a listed site that relays to another site isn't caught.

Turned down

A firewall script inside the pod (needs admin rights in the pod); address-range rules only.
0007
Logins and keys stay out of Git and out of the image

Our Claude login lives on the sandbox's own disk. The worker's key lives in a Kubernetes Secret and only works for one agent queue.

Accepted
Details

Why

Remote Control needs a full Claude sign-in; a long-lived token from setup-token can't start it. The worker key can only claim work from one queue, and Anthropic asks for it to be kept in a secret store.

The cost

If a workspace were compromised it could use our subscription and reach the GitHub repos its token allows. It still couldn't reach Vault, the Kubernetes API or the rest of the cluster.

Turned down

An organisation API key in the workspace; baking a login into the image.
0008
Each sandbox gets its own disks, and the system files are read-only

A workspace disk and a home disk per sandbox, kept even if the sandbox is removed.

Accepted
Details

How

local-path volumes for /workspace and /home/agent, temporary space for /tmp, read-only root file system.

Turned down

Our NAS (its NFS shares don't work with pod user namespaces); a writable root file system.
0009
You reach the workspace from the Claude app, and nothing can connect in

Claude Code calls out to Anthropic's relay, so the sandbox needs no open port and no public address.

Accepted
Details

How

claude remote-control in server mode, up to eight sessions, each in its own copy of the project. One sign-in over kubectl exec at setup.

Turned down

SSH into the pod; a browser terminal sharing the sandbox's disk; one session per process.

Note

ADR-0017 suggests a different product for enterprise use.
0010
One always-on agent worker for now, one sandbox per session later

Today, sessions for the same queue share the worker's folder. That's fine for us, not for a shared company setup.

Accepted
Details

Why start simple

A sandbox per session needs something that creates pods on demand and a key per session. That's more moving parts than a first deployment should carry.

Next

Kubernetes Jobs started per task, or the agent-sandbox controller (ADR-0015).
0011
Everything ships through GitOps

To change a sandbox, we change a file in Git and ArgoCD makes the cluster match.

Accepted
Details

How

Two version pins (chart version and container image), keys created outside Git, rolled through the same pull-request flow as the rest of the homelab. Updated by 0016.
0012
We watch it with the tools the cluster already has

Logs go to Loki, a debug switch shows every refusal, and a health check restarts a stuck pod.

Accepted
Details

Why the debug switch is off by default

It logs every command the agent runs, which is more than we want in long-term logs.

Routine

Check for new versions of the sandbox runtime, Claude Code and the ant CLI once a month.
0013
We measure the build against published security guidance

Every control gets a status (met, partial or gap) and a note on what a company would need to add.

Accepted
Details

The three gaps

A separate kernel per sandbox; credentials that never enter the sandbox; tamper-proof, centralised logs.

Turned down

Picking one framework only; claiming the strictest Kubernetes pod security level (it would be false).
0014
The project lives in its own repository

The chart, the container image, the docs and this site all live in one place, and the homelab just points at the published chart.

Accepted
Details

History

We first put the chart inside our homelab-charts repo, then moved it out the same day, before anything was committed.
0015
The long-term goal: a control plane over swappable sandboxes

Add a Kubernetes controller that manages sandboxes per session, then a stronger isolation layer when we have the hardware.

Proposed
Details

Why

This is the target our principal engineer described (see North star). What we have today is the bottom layer of it.

Next steps

Install kubernetes-sigs/agent-sandbox; add a microVM runtime once a server supports it; evaluate NVIDIA's OpenShell against Anthropic's sandbox runtime.
0016
Each sandbox is one small file in a folder

Adding a sandbox means adding a five-line file. ArgoCD turns each folder into its own running sandbox.

Accepted
Details

Why

A single list of sandboxes doesn't scale, and Helm can't merge lists from separate files. The first rollout also failed on a short definition, which is why every kind now has sensible defaults.

Versioning

The chart stays at 0.1.0 until other people start using it.
0017
Anthropic runs the brain; we run and watch the hands

The Claude Console manages sessions, keys and spend, not our sandboxes. Fleet health comes from our own dashboard.

Proposed
Details

What we found

No Anthropic dashboard lists or scales the sandboxes. For Claude Code, Anthropic's "self-hosted environments" product (Team and Enterprise) does give admins a runner view and metrics.

Plan

A Grafana fleet dashboard, an exporter for the agent queue numbers, autoscaling with KEDA, and moving workspaces to self-hosted environment runners in an enterprise. See the Fleet page.
